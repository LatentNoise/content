Two words change meaning in this release, and one of them will change what
your automation sees.

## `succeeded` now means everything succeeded

A job's terminal status used to be computed from its outputs alone, and never
looked at whether a step had failed. Two ordinary situations reported success
dishonestly:

- a **playlist where one member died** — five videos of six, a non-empty
  output, "succeeded";
- a **delivery refused by the library** — the artifact was counted before the
  delivery step failed, so an operator got a green job and an empty folder.
  Anyone whose Plex or Jellyfin library is owned by another user was getting
  exactly this.

Both now report **`partially_succeeded`** (ADR 0021). The same runs, a
different word. Nothing that failed before now succeeds: the rule only ever
softens a success, never hardens a failure.

**If you key automation on `status == "succeeded"`, read this line.** Those
runs will start reporting `partially_succeeded`, which is the point — they were
never complete. The CLI carries it into the shell: `content … --watch` and
`content watch <job>` now exit **2** for partial, **1** for failed or
cancelled, **0** for success. A script that treated any non-zero as failure
keeps working; one that treated `0` as "everything arrived" was already wrong
and now finds out.

## `original` is a language you can ask for

```json
{"selection": {"audio_languages": ["original", "fr"]}}
```

*The source's own voice if it has one, otherwise French.* A playlist could not
express this at all before — the original language is a per-video fact, and
members are deliberately not analysed at submission (ADR 0019), so a channel's
back catalogue in five languages came back in whatever the default track
happened to be.

The token is resolved per resource at plan time, by the same code that plans a
lone video, so a playlist member and the same video submitted alone reach the
same answer. It composes with ordering instead of replacing it — a position in
the list, not a flag. A source declaring no original drops the token, falls
through to the next preference and says so with a `partial_output` warning.
Audio language lists accept it; subtitle lists and translations refuse it,
because "the original" has no meaning for a translated track. `content_sdk`
exports it as `ORIGINAL`, and HomeTube offers it for playlists (ADR 0022,
now accepted and implemented).

## Artifacts are named for what they are

Observed in a real library:

```text
Random tour through the Blender Institute - en.json      ← a transcript
twenty one pilots Stressed Out … - transcript - en.json  ← also a transcript
```

Both are transcripts. The first was requested alone, the second beside a video,
and `… - en.json` is unidentifiable in a folder. The naming rule let the
*request shape* decide: a single-output request named its output bare whatever
its type. So a lone summary was `Title.md`, indistinguishable from a Markdown
export of the same page, and a lone thumbnail was `Title.jpg` — which ADR 0017's
own text already said should be `Title - thumbnail.jpg`.

The rule is now about what the artifact **is**. Only a rendering of the resource
itself — video, audio, markdown, document_text, pdf — takes the bare name.
Everything about the resource says so, always, whatever else was requested.
"Summary + a PDF of it" is now `Title - summary.md` + `Title - summary.pdf`
rather than crowning the rendering.

**Nothing already in your library is renamed** — that directory is yours. But
if you asked for transcripts, summaries or subtitles *alone*, new files gain
their qualifier, and anything keying on the old filename should be checked.

## Deliveries are visible, and collisions are announced

Delivery left no trace in the event stream at all: the library gained a file
and the only record was a `delivered_path` column nothing surfaced. There is
now an **`artifact.delivered`** event with the path — and with `renamed_from`,
which is empty unless the name was already taken by *different* content.

That is the `…-1` case. Two different videos can share a title, so the counter
is right, but it used to fire silently and you met the clone weeks later with
no way to tell which job produced which. It answers "was the name taken?", not
"was the name cleaned?" — a slash becoming " - " is ordinary display naming and
is not reported as a clash.

## A filename is claimed, not just found free

Two places picked a name by looking and then writing — artifact promotion, and
delivery into your library. Between the check and the write, another writer can
take the same name and one file overwrites the other. Reproducing the old
algorithm under a thread barrier loses that race **200 times out of 200**, at
two concurrent writers as reliably as at eight — and two is the shipped default
(`CONTENT_MAX_CONCURRENT_JOBS`), with a collection's members adding more, all
delivering into one folder.

Names are now taken by *creating* them: the bytes are staged beside the
destination, then hard-linked onto the first free name, so name and content
appear in one atomic step. Delivery gained something it never had along the
way — it is now atomic, where before `copy2` grew a file in place and a
watching Plex or Jellyfin could scan a half-written video. Filesystems without
hard links (some network and FAT-family mounts) fall back to an exclusive
create plus a rename.

## Uploads that expire are now actually collected

0.5.0 documented a TTL and enforced nothing: `expired_uploads()` existed and
nobody called it, so an expired upload was refused at resolution while its bytes
stayed on disk forever. The sweep now runs beside the queue on its own clock.

Studio's file picker also stopped guessing: the ceiling is **200 MB** there, and
the widget says so. It is lower than the API's 2 GiB on purpose — Streamlit
buffers an upload in the UI container's memory — and for genuinely large files
the SDK streams from disk.

## Cookies tell you which of three problems you have

An age-restricted download used to fail with `yt-dlp exited with code 1.` The
engine knew it was an authentication failure and never said anything a user
could act on. Worse, one classifier branch was unreachable: "Sign in to confirm
you're not a bot" matched the generic auth patterns, which were tested first.

The failure now names which of three situations it is: **no credential
configured** (with how to add one), **a credential declared but its file
unreadable** — so the download *ran anonymously*, which is the quiet one — or
**cookies used and still refused**, meaning they have expired. The analysis
error carries `details.cookies` as `none | missing | used` so a client can react
without reading prose.

From a clone, `make cookies FILE=~/Downloads/cookies.txt` installs an export:
it checks the file is a Netscape jar carrying a YouTube cookie, keeps any
previous one, and prints the next command. Getting the filename wrong is the
classic failure, and that is what it removes.

## Also in this release

- **The CLI follows the event stream** instead of polling every two seconds.
  The SSE endpoint already existed; no client could consume it. The SDK gains
  `stream_events`, with the read timeout disabled for the stream alone — a long
  quiet download is not a dead connection.
- **`server.json`** is committed and validated, and publishing a release now
  announces `content-mcp` to the **official MCP registry** automatically, after
  the PyPI upload it depends on. See
  [docs/operations/mcp-registry.md](https://github.com/LatentNoise/content/blob/main/docs/operations/mcp-registry.md).
- **HomeTube gains a transcript-format control** (JSON canonical, text
  readable), and Studio's stopped offering `srt`/`vtt`, which the contract
  refuses.
- **The README** is reorganised around its clients — one section each, with its
  own screenshot — with HomeTube and its demo above the fold.

## Proposed, awaiting a decision

**ADR 0023 — retention.** Measured on a real instance first: with delivery on
by default, every delivered artifact exists twice. So the question is not "how
do we delete a user's downloads" but "how do we stop keeping two copies". The
delivery library is never eligible, enforced by a test; reclaiming bytes is not
forgetting, since the artifact row keeps its filename, checksum and provenance
and the content endpoint answers 410 rather than a 404 that would claim it never
existed.

**ADR 0024 — authentication.** The "no auth in V1" position was inherited from a
list written when Content was one person's tool. Uploads made the API a write
primitive and the repository went public, so it was re-examined. The answer is
still no, but now for reasons that can be argued with.

Neither is implemented.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No migration to run. Two behaviour changes are worth a moment before you
upgrade an automated setup: jobs with a failed step now report
`partially_succeeded`, and artifacts of a *single-output* request for a
transcript, summary or subtitles gain their qualifier in the filename.
