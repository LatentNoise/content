The hosted instance becomes something you can open to strangers: the routes
that describe the machine are reserved to its operator, one person cannot fill
the disk or hold the queue, what accumulates can be deleted or swept, and each
person's files live in one directory. And the self-hosted install gets
something back: its disk looks the way it did before ownership, with no
`local/` level for a user that will only ever be one.

**If you self-host, upgrading changes nothing you asked for.** Every new limit
is off, the sweep is off, and the storage layout defaults to the flat tree.
The one visible change is on disk, and it is a return: `jobs/local/<job>`
becomes `jobs/<job>` again on the next start.

## Operating is a privilege, not more data

Four routes described the *installation* rather than anyone's work — disk
paths and occupancy, the shared analysis cache. Owner filtering meant nothing
for them: they have no owner. They had a privilege, and nothing enforced it.
The day the temporary password in front of the public deployment came off,
`/api/v1/storage` printed the server's own paths to anyone who asked
([ADR 0035](https://github.com/LatentNoise/content/blob/main/docs/architecture-decisions/0035-operating-is-a-privilege-not-more-data.md)).

An operator is now **a flag on an ordinary account**, not a second kind of
credential: same sign-in, one extra capability. `CONTENT_OPERATOR_EMAILS`
grants it the moment such an address signs in, which is how the first operator
exists — there is nobody to promote them. Unlisting an address does not revoke
it: withdrawing a privilege is an act on the account, never a side effect of
editing a file. On a self-hosted instance the single local user is always the
operator, which is a fact about that owner and not a branch on the mode.

`/api/v1/storage` was **split rather than closed**. The plain name now reports
what *you* hold — your jobs, uploads and delivered files, plus a total, and no
paths. The installation-wide view moved to `/api/v1/operator/storage`. Closing
the route would have been an administrator's answer, correct and useless to
the person who wants to know how much space they use. `/api/v1/cache` and its
purge are operator-only; `/api/v1/config` stays open, since it holds no data
and a client needs it to know what to ask for. An ordinary user gets 403, not
404: the route plainly exists.

## What one owner may use

Three limits, all off by default, because a self-hosted instance is not a
customer of itself and an operator is never counted
([ADR 0036](https://github.com/LatentNoise/content/blob/main/docs/architecture-decisions/0036-what-one-owner-may-use.md)):

```
CONTENT_QUOTA_MEDIA_MINUTES_PER_MONTH   minutes of SOURCE media, rolling 30 days
CONTENT_QUOTA_STORAGE_BYTES             bytes held right now, not a running total
CONTENT_QUOTA_CONCURRENT_JOBS           unfinished jobs at once
```

The unit is the decision. **Media is counted in seconds of source, never in
processing time.** A source's duration is known at analysis, before any work
happens, so a refusal lands before the expense rather than after it — and it
does not charge twenty times more for a 4K video than for an audio clip at
identical service rendered. A playlist counts every member; an unreadable
duration counts as zero rather than turning every unusual source into a
support ticket.

A refused submission carries the stable code `quota_exceeded` and names the
limit, the usage and the allowance. `GET /api/v1/usage` reports the same
numbers, in the same release as the enforcement, because a limit a person
cannot watch themselves approach is a trap rather than a rule.

## A quota needs a way out

Nothing was ever deleted. ADR 0023 had sat at "proposed" for a month, and the
engine had two DELETE routes, for uploads and API keys — neither frees a byte
of what accumulates. A storage ceiling with no way to free space is a dead end.

`DELETE /api/v1/jobs/{id}` removes one of your jobs and everything it holds. A
running job answers 409 rather than being deleted from under itself: cancel is
a different verb. `?delivered=true` also removes the copies the job put in the
library, and that is **off by default**.

`CONTENT_RETENTION_DAYS` turns on an unattended sweep of finished jobs older
than the window, on the existing housekeeping tick. Off by default: an upgrade
must not start deleting data nobody asked to delete.

**The delivery library is never swept.** Files there have been renamed, filed
into folders, added to playlists, and a media server indexes them. An
unattended job that takes a film out of someone's collection is not a feature,
whatever the window says. Retention, not the per-person quota, is what bounds
total disk on a hosted instance: a seven-day window makes occupancy follow the
flow of work rather than the number of accounts.

## One directory per person, and none when there is one

ADR 0030 inserted an owner level inside each storage family. Everything one
person owned was spread across three trees, uploads had not even received the
level, and every self-hosted install paid for a case it does not have
([ADR 0037](https://github.com/LatentNoise/content/blob/main/docs/architecture-decisions/0037-one-directory-per-person-and-none-when-there-is-one.md)).

```
flat        <data>/jobs/<job>  <data>/tmp/<job>  <data>/uploads/<id>
per_user    <data>/users/<owner>/{jobs,tmp,uploads,resources,output}/
```

`CONTENT_STORAGE_LAYOUT` is a policy value read by one module and nothing else;
no route or sweeper knows which layout is in force. It defaults from the
authentication mode in exactly one line: `flat` when nobody signs in,
`per_user` when people do. A flat tree with sign-in is refused at startup — it
holds exactly one owner by construction.

The library goes with the person: `users/<owner>/output`, next to the rest of
what they own, and a mounted volume can still be placed there. `delivery_scope`
keeps `shared` for a family instance and `off` for none. The analysis cache and
the analysis scratch belong to nobody and stay at the data root in both
layouts.

The migration runs on every start and brings any earlier shape — pre-ownership,
the 0.8.0 owner level, the other layout — to the configured one. It is
idempotent, interruptible, and conservative: a directory that does not look
like an owner id is left where it is and mentioned once. Upload rows keep their
recorded absolute path, but an upload's location is now **derived from the
layout at read time**, which is what makes the migration a plain move.

Reserved and empty: `resources/`, where raw downloads will live indexed by
resource rather than by job, so that asking for the last minute of a video does
not re-fetch what the first minute already brought. Its retention and quota
treatment are a separate decision.

## Also

- The Console shows your own usage on the Access tab, reads the installation
  view through the operator route, and says so plainly when the person looking
  is not the operator.
- The ownership guard-rail accepts either door, a plain identity or an identity
  plus the privilege, and still fails on a route that resolves neither.

## Upgrading

Nothing to do. Every limit defaults to off, the sweep is off, and the layout
defaults to `flat` for a self-hosted install — whose disk is filed back to
`jobs/<job>` on the next start, leaving at most an empty `jobs/local/`
directory behind.

A hosted instance (`CONTENT_AUTH_MODE=token`) is filed into
`users/<owner>/` on the next start. Set `CONTENT_OPERATOR_EMAILS` before
switching, so the first sign-in of that address carries the privilege, and
size `CONTENT_RETENTION_DAYS` before the quotas: it is the setting that bounds
the disk.
