A fix release for the MCP server, found by registering it with an agent and
driving it as one — not by testing it.

## An agent's mistake is refused, not obeyed

`{"type": "subtitles", "languages": ["es"]}` — per-output settings flattened
onto the spec instead of nested under `options`, the guess an agent actually
makes — was **accepted**. The intent was dropped, a job producing *English*
subtitles started, and the caller was told it succeeded. For a client that
cannot inspect the result, silently answering a different question is the
worst possible failure.

Unknown keys are now refused with the shape that works:

```text
unknown key(s) ['languages'] on the 'subtitles' output. Per-output settings
belong under 'options' — for example {"type": "subtitles", "options":
{"languages": ["es"]}}, not {"type": "subtitles", "languages": ["es"]}.
```

The engine's own models have always forbidden unknown fields; the MCP layer
was quietly undoing that by reading the keys it recognised and discarding the
rest. The `generate` tool's description now carries the example too, so the
first attempt is usually right.

## A failed job says why it failed

`get_job` answered `{"status": "failed", "error": ""}`. The engine records a
failure on the step that failed, so the job's own error is usually empty —
leaving an agent knowing only that something broke, with nothing to tell its
user and no basis for trying differently. Failures now travel with their
reason:

```json
{"status": "failed",
 "error": "provider_error: yt-dlp exited with code 1.",
 "failures": [{"step": "acquire_subtitles_subtitles_main",
               "operation": "media.acquire_subtitles",
               "error": "provider_error: yt-dlp exited with code 1."}]}
```

`content_sdk`'s `JobData` gains a declared `steps` field, rather than relying
on undeclared attributes surviving validation.

## Collections explain themselves

Resolving capabilities on a playlist reports video, audio and subtitles as
*unavailable* — true of the collection resource, and useless as guidance,
since the same playlist produces all of them with `scope: "each_item"`. The
web UIs escape this by knowing the rule out of band; an agent does not. The
server's instructions now state it, so the next agent asks the right
question. The underlying gap is tracked for a contract-level answer.

```bash
uv tool upgrade content-mcp        # or: uv tool install content-mcp

```
