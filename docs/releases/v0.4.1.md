One fix, found by smoke-testing the published 0.4.0 image rather than by a
report: a transcript could come back in a language nobody asked for, and nobody
speaks in the video.

## A transcript is the text of what was said

Asking for a transcript with default options on an ordinary English video
planned its subtitle acquisition in **Afar** (`languages: ['aa']`). The engine
would have downloaded Afar subtitles and delivered them as the transcript. It
only surfaced at all because YouTube answered `429` on that particular track —
had it answered `200`, the job would have "succeeded" with a file whose contents
were unrelated to the video.

The cause was a tie-break. With the resource's language unknown, the resolver
fell back to the first available subtitle track in alphabetical order. That is
harmless where a source offers two or three tracks, and absurd on YouTube, which
publishes auto-*translated* subtitles in around a hundred languages — `aa` sorts
first in every one of them.

Analysis reports neither `resource.languages` nor `media.original_audio_language`
for these sources, so what was spoken has to be inferred. A hand-written track is
almost always in the video's own language, which makes it the usable stand-in.
The order is now:

1. the language analysis declares for the resource, when it knows one;
2. otherwise, among **manual** tracks: a language this installation is
   configured for (`CONTENT_LANGUAGE_PRIMARY` and its secondaries), then
   English, then the first one;
3. only if no manual track exists at all, the same order among automatic tracks;
4. alphabetical order survives solely as the final tie-break within one kind.

**One consequence is deliberate.** A French installation asking for a transcript
of an English video now gets the English transcript, not a machine translation
into French. Preferences choose among what was genuinely said; they do not turn
a transcript into a translation — `translation` is a separate output, and asking
for it remains the way to change language.

The operator's configured languages reach the planner for the first time to make
this possible, threaded as an optional argument so no existing caller changes.
Eleven tests pin the rule down, including the regression stated plainly: Afar is
never chosen while a sane option exists.

Summaries and chapters derive from the same chain, so they inherit the fix.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No migration, no configuration change. If you asked for a transcript on 0.4.0
and got a file in a language you did not expect, request it again — and if you
were working around this with an explicit `options.language`, you can keep doing
so: an explicit request has always won and still does.
