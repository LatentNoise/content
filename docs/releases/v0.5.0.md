Content stops assuming your files are already on the engine.

Until now a `file` source meant *a path the engine could already read*. If the
engine ran on a homelab and you did not, nothing on your machine could be
submitted at all — the topology this project recommends had a hole in it. This
release closes it in both directions: files go up, artifacts come back.

## Send a file from your own machine

`POST /api/v1/uploads` stores bytes a client supplied and returns an id;
`{"type": "upload", "upload_id": "upl_…"}` then references them like any other
source. This implements the `upload` type reserved in the contract since the
beginning (ADR 0020).

The invariant that keeps it small: **upload is acquisition, never processing.**
Once resolved, an uploaded PDF behaves exactly like the same PDF sitting on the
engine's disk — same analysis, same capabilities, same planning, naming,
delivery and provenance. There is no second pipeline and no branch on source
type beyond resolution.

Every client gained the shortest form of it:

- **Studio** offers "From this device" beside "On the server" — one idea, two
  supply routes. The user never meets the word *upload*.
- **The SDK**: `source = client.upload_file("~/report.pdf")`, sync and async,
  plus `upload_bytes()` for callers that never had a file on disk.
- **MCP**: a local path handed to `analyze_source` is uploaded transparently, so
  *"summarize ~/Documents/report.pdf"* works against a remote engine.

A path given to MCP is always a path on **your** machine. It is never assumed to
mean the same thing on the engine, even when the engine looks local: identical
strings on two hosts do not imply identical filesystems, and guessing wrong
would read a different file.

**Uploads and `file` sources stay governed separately.**
`CONTENT_ALLOWED_INPUT_ROOTS` remains operator policy for `file` — empty still
means the feature is off — while the upload store is engine-owned and always
readable back. An earlier attempt merged the two and silently repealed the
policy; the separation is now pinned by a test.

An upload expires `CONTENT_UPLOAD_TTL_HOURS` (default 24) after its **last
use**, not after creation, so retrying a job still finds its input.
`upload_expired` and `upload_not_found` are distinct answers, because "send the
file again" and "your reference is wrong" are different instructions.

**Read the security note if you expose the API.** This is the first endpoint
that lets a caller write bytes to the engine's disk: before it, the worst an
unauthenticated stranger on your network could do was make the engine *fetch*
something. `CONTENT_MAX_UPLOAD_BYTES` (2 GiB, counted while streaming rather
than trusted from the header), `CONTENT_UPLOADS_TOTAL_BYTES` (20 GiB) and the
TTL bound the damage, and upload ids are random enough to make enumeration
impractical — but an id is identity, not authorization. One more reason for a
reverse proxy.

## Bring an artifact back to your machine

The mirror image, for MCP callers: `download_artifact(artifact_id, destination)`
saves an artifact onto the machine running the MCP server, which for a homelab
engine previously meant reaching for `scp`. Everything lands inside
`CONTENT_MCP_DOWNLOAD_DIR` (default `~/Downloads/Content`); a destination
outside it is refused rather than quietly moved back inside.

The other half of that problem was not a missing feature. The engine already
delivered by default and already exposed the library's folders — the agent
simply never asked for one, so everything piled up in the root. The MCP
instructions now steer it to choose a folder and to report `delivered_path`
rather than an artifact id.

## Collections run their members concurrently

`CONTENT_COLLECTION_MEMBER_CONCURRENCY` (default 2) lets a playlist download
two members at once. It is a politeness bound toward the provider, not a
throughput dial — and it applies **per job**, so it multiplies with
`CONTENT_MAX_CONCURRENT_JOBS`: the shipped defaults allow up to four
simultaneous downloads from one host.

Under `fail_fast`, a failing required member stops members that have not
started; members already in flight run to completion, because a valid artifact
is not worth throwing away mid-download. Cancellation reaches in-flight members
through the same check every step already honours.

## Documents that are true

- **HomeTube's configuration is documented**, with the language settings shown
  by worked example rather than by rule — including that
  `CONTENT_LANGUAGE_PRIMARY_INCLUDED_IN_SUBTITLES` ships as `false` while the
  engine's own default is `true`, and that it excludes only the primary.
- **The contribution policy no longer promises a setting GitHub does not have.**
  Five documents claimed pull requests were "turned off in the repository's
  settings"; no such setting exists for a public repository. They now say what
  is true and applied: unsolicited pull requests are closed without review.
- **`SECURITY.md`** stops pointing at a private-reporting form that is not
  enabled; email is stated plainly as the route.
- **The `user:` remedy** for a delivery library owned by another uid is
  documented as needing its own `chown`, because the container's adoption step
  only runs as root — without it the engine cannot create its database.
- **Chrome Web Store submission material** is written and reviewed: listing
  texts, single-purpose statement, per-permission justifications, data-use
  declarations and a privacy policy.

## Proposed, awaiting a decision

Two ADRs ship as documents, not behaviour. **0021** argues that a job should not
report `succeeded` when a step failed — today a playlist with one failed member,
or a delivery refused by a library owned by another user, still reports success.
**0022** proposes `"original"` as a reserved value in `audio_languages`, so a
playlist can be requested once and come back each video in its own language.
Neither is implemented; both change published behaviour and want a decision
first.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No migration to run: the uploads table is created on start. Nothing else
changes behaviour for an existing installation — the new limits only apply to a
feature that did not previously exist, and member concurrency defaults to 2,
which you can set to 1 to restore strictly sequential playlists.
