Two fixes for the same real failure: a first HomeTube run on a homelab asked
one YouTube URL for a video and an audio file. The video was perfect. The
audio came back `HTTP Error 403: Forbidden` and the job failed.

## Audio is taken out of the video, not downloaded again

The two outputs were fetching **the same opus stream twice** — merged into the
video by `bv*+ba`, then again on its own, seconds later. The waste was the
smaller half of the problem: a second request is a second chance to be
refused, and that is exactly what happened.

The audio output now depends on the video's acquisition and copies the track
out with `ffmpeg -c:a copy`. On a live job the audio step performs no download
at all, and the extracted file's audio packets hash identically to the video's
own track — the same bytes, not a re-encode. One request, one download, half
the bandwidth, and the failure mode is gone rather than retried past.

The derivation is refused wherever the extracted track would not be exactly
what the second download produced: an explicit audio format (a transcode,
which a copy cannot do), SponsorBlock settings that differ between the two
outputs (it is applied during acquisition, so it is baked into the file), a
different language selection, a collection's `each_item` scope, and a file
source, which never downloaded anything twice. Silently returning a different
audio file than was asked for would be worse than fetching twice.

It reads the *acquisition*, never a later transform — so a video output that
is cut still yields uncut audio, because the audio output never asked to be
cut. An installation without ffmpeg keeps the download it always had.

## Audio acquisition retries like video always did

Video had carried a fallback ladder since the beginning (codec profiles ×
player clients) and had been recovering from transient refusals invisibly.
Audio had a single shot, which is why one refusal ended the output.

Audio now shares that resilience, with the default client tried twice before
any alternative: measured, `ios` and `web` cannot serve audio-only formats for
that video at all ("only images are available" without a PO token), so
reaching for them before a plain retry would replace a recoverable blip with a
different failure. A media URL is signed and short-lived and every yt-dlp
invocation re-extracts it, which is precisely why running the same command
again is the fix. Cancellations and timeouts still stop immediately — they are
decisions, not hiccups — and provenance records the retry.
