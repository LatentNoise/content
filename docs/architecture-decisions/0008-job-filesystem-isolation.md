# ADR 0008 — Per-job filesystem isolation

Status: accepted (2026-07-17)

## Context

HomeTube organizes its cache per resource (`tmp/videos/<platform>/<video_id>/`), which is efficient at never re-downloading but entangles lifecycles (one cleanup can break another job). Content needs independent lifecycles (separate retention for outputs/work/logs), auditability, and a replaceable storage boundary.

## Decision

Every job owns an exclusive tree, managed by the `storage` module alone:

```text
$CONTENT_DATA_DIR/jobs/<job_id>/{sources,work,artifacts,logs,snapshots}/
```

- Every execution write goes through `storage` under the job; filenames are generated by the backend (`sanitize_filename`).
- `work/` is purged at the end of the job; `artifacts/` obeys its own retention; `snapshots/` (request, analysis, plan, result) is immutable.
- Artifact promotion is **write-then-register**: the file is moved into `artifacts/` before the DB row — never an artifact registered without content.

## Consequences

- Per-job cleanup and debugging are trivial; the tree is relocatable (relative paths in the DB).
- Accepted cost: the same resource requested by two jobs is downloaded twice. The **per-resource** cache will come back through `execution.reuse_existing`, indexed by the `artifacts` table (resource identity + checksum), not by scattered `status.json` files.
- V1 limit: snapshots (including the plan) live only on the filesystem; the DB and the files must share the same volume.

## Alternatives considered

- **A per-resource cache directly** (the HomeTube model): optimal on bandwidth but couples lifecycles and complicates per-job retention; deferred to `reuse_existing`.
- **Everything in the DB (blobs)**: simplifies consistency, but SQLite is not a store for multi-GB media; it contradicts the future S3/MinIO boundary.
